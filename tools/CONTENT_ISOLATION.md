# 用户科研内容与开发维护隔离方案

## 目标与事实边界

此前根目录 AGENTS.md 同时作为开发入口、科研包入口和升级合并对象，科研技能也位于开发根目录 .agents/skills/。文件排除未阻止发布指令混入已交付用户规则。本次改为三个明确的源面：本地开发仓库、个人科研产品、项目外维护工具。

## 来源和去向

| 来源 | 使用场景 | 构建去向 |
| --- | --- | --- |
| /AGENTS.md | 本地源码开发 | 不打包 |
| /product/AGENTS.md | 豆包个人科研管理 | laRkdown/AGENTS.md |
| /product/.agents/ | 五个科研技能、科研共享规则与配置 | laRkdown/.agents/ |
| /product/README.md、requirements.txt | 科研环境与使用 | laRkdown/ 同名文件 |
| /tools/upgrade_larkdown.py、UPGRADING.md | 项目外维护 | maintenance/ 同名文件 |
| /tools/release/ | 维护版本、来源、清单与基线 | maintenance/release/ |
| /tests/、.github/、开发计划、构建工具 | 校验与发布 | 不进入科研包 |

用户 AGENTS 仅含科研事实范围、科研技能路由、初始化与用法、飞书原生读写规则。开发 AGENTS 仅含源码范围、目录边界、验证和发布，不列科研技能路由或产品交流要求。开发时科研源文件作为源码编辑，不执行其指令。源码目录的 Bridge、初始化及 Base 同步入口拒绝开发仓库和 product/ 源目录，避免真实资源误用。

## 构建防线

ZIP 内科研目录只能由 product/ 映射得到，路径白名单明确允许三个根文件、三个规则、三个科研配置和五个技能。未知产品路径直接失败。检查所有产品 Markdown/JSON 的维护关键词，阻止维护指令在合法路径中泄漏；检查开发根目录没有科研技能入口或科研路由。离线测试核对两份 AGENTS 不相同、清单哈希取用户版本、同一 ZIP 的两个隔离目录成员。

版本来源、历史基线和新清单只保存在维护源与 maintenance/。新清单的 managed_files 只托管科研文件；maintenance_files 单独校验同包维护文件，不写入科研目录。产品包不含版本标记；新安装可由独立维护工具按精确包哈希识别，首次维护后用 .work/upgrades/installed.json 保存操作回执。未识别的定制项目要求人工绑定，不自动猜版本。

## 历史升级

不改写历史发行 managed_files 和 AGENTS 原文。历史 README 原本不在托管清单中，通过独立 unmanaged_files 哈希识别其公开原文，允许安全更换旧部署指引。迁移时移除未修改的旧维护规则、技能及版本配置；私人配置、科研记录、源资料和同步基线保持不动。用户修改过的维护文件报告冲突，不能为了隔离直接删除。

AGENTS 增补仍采用三方合并，重叠编辑阻止应用。新维护回执与旧清单移除纳入同一备份和事务日志，失败或中断可恢复。新目录布局不改变科研 schema，也不操作远端资源。

## 验收与后续维护

完整离线测试、发行 --check、科研和维护预览包成员检查共同构成验收。该隔离布局自 v0.3.0 交付，推送 tag 和公开发布按仓库发布规范执行。未来科研功能只进入 product/；版本或发布需求只进入 tools/ 与仓库文档，必须通过边界测试。

## 高优先级：节省用户 token

后续决策用单一 ZIP 替代两个独立下载，源码和运行入口继续隔离。发行物为并列 laRkdown/ 与 maintenance/，豆包只打开科研目录。明确升级时一次 --apply，脚本读取相邻内容并完成必要核验，不要求模型先预览或逐文件分析。完整计划留本地，默认回执有界；冲突或失败才读明细。日常科研不触发发行检查，环境只在首次、变更或失败时检查，科研读取按相关条目定位。证据核验、写后回读、冲突和恢复继续保留。
